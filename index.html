Relational Cardinality & Explicit Rationale

Every relationship modeled with its exact business, security, and data integrity reasoning.

User Message

1 : N One-to-Many

Foreign Key: Message.sender_id

Why One-to-Many?

A user composes multiple messages across their lifetime (advice to children, wedding letters, reassurance, future self notes). Each individual message has strictly one unique author/sender who owns and encrypts the content.

User Contact

1 : N One-to-Many

Foreign Key: Contact.owner_id

Why One-to-Many?

Each user curates their own private address book of recipients (mother, spouse, friends, future self). Contacts belonging to User A must remain private and never leak into User B's recipient list.

User InactivitySettings

1 : 1 One-to-One

Primary Key = Foreign Key: user_id

Why One-to-One?

A user can have exactly one active proof-of-life policy (global check-in interval, grace period, and designated trustee). Enforcing a 1:1 relation guarantees zero ambiguity or conflicting switch states for a given account.

Message Delivery

1 : N One-to-Many

Foreign Key: Delivery.message_id

Why One-to-Many?

Vital state separation: When a message is sent to multiple recipients, each recipient has an independent lifecycle (Recipient A opened it today, Recipient B clicked "Open Later", Recipient C hasn't opened yet). Each recipient also requires their own unique, single-use public link token (access_token_hash).

Message MessageMedia

1 : N One-to-Many

Foreign Key: MessageMedia.message_id

Why One-to-Many?

A single composed message can attach multiple media files (e.g., 1 voice memo + 2 photos + 1 video). Normalizing attachments into a separate table allows upload progress tracking, storage quota calculation, and short-lived signed URLs without bloating the message record.

Message Contact

N : M Many-to-Many

Join Table: MessageRecipient (message_id, contact_id)

Why Many-to-Many?

One message can be addressed to multiple family members simultaneously, and one contact (e.g., "Mother") can receive multiple distinct messages from the user across different years and occasions.

User Device

1 : N One-to-Many

Foreign Key: Device.user_id

Why One-to-Many?

A user can install the app on multiple physical hardware devices (e.g., iPhone, iPad, Android tablet). Push notifications (FCM) for proof-of-life check-ins ("Where have you been? Everything OK?") must reach all active devices.

User OTPCode

1 : N One-to-Many

Foreign Key: OTPCode.user_id (nullable)

Why One-to-Many?

A user requests verification passcodes at different times (email verification, password reset, recipient unlock). Each OTP is a distinct event with its own 5-minute expiry timestamp and 5-attempt brute-force counter.

User Checkin

1 : N One-to-Many

Foreign Key: Checkin.user_id

Why One-to-Many?

The proof-of-life engine repeatedly prompts the user. Over months or years, the user responds "I'm fine" dozens of times. An immutable historical ledger is kept to prevent false releases and provide an unquestionable audit trail.

User TrusteeConfirmation

1 : N One-to-Many

Foreign Key: TrusteeConfirmation.user_id

Why One-to-Many?

If an inactivity sequence triggers, a trustee confirmation request is dispatched. If the user cancels the sequence and goes inactive again later, a new confirmation cycle starts. Each attempt requires its own token hash, IP, and decision record.

Plan User

1 : N One-to-Many

Foreign Key: User.current_plan_id

Why One-to-Many?

A membership plan (Free, Monthly, Business) is a shared template defining limits (max_messages, storage_years). Thousands of users belong to the Free plan, but each user has exactly one active plan tier.

Contact User

N : 1 Optional Many-to-One

Foreign Key: Contact.linked_user_id (nullable)

Why Many-to-One?

If a recipient contact's email matches an active user account in the app, it links to that User so messages appear directly in their in-app /inbox. Multiple senders can independently save the same person in their contacts.

Comprehensive Table Deep-Dive

Functional breakdown, data security attributes, and inbound/outbound relations for every table.

User

Core Identity

Function & Role in Catalog

Represents the primary user profile, handling authentication, encryption master keys, and activity heartbeats. The last_active_at column is updated on every API request and "I'm fine" tap, powering the on-demand proof-of-life engine without requiring background cron daemons.

  • Message (sender_id) 1 : N

    Why 1-to-N: A user creates multiple messages; each message belongs to one sender.

  • Contact (owner_id) 1 : N

    Why 1-to-N: A user has a private address book of recipients.

  • InactivitySettings (user_id) 1 : 1

    Why 1-to-1: A user has exactly one proof-of-life dead man's switch policy.

Message

Encrypted Vault

Function & Role in Catalog

Houses composed messages and their delivery triggers (instant, date, occasion, inactivity). For total privacy, message bodies are encrypted with AES-256-GCM (body_encrypted, body_iv, body_tag) and are only decrypted when viewed by the sender or verified recipient.

  • MessageMedia (message_id) 1 : N

    Why 1-to-N: A message can have multiple voice, photo, or video attachments.

  • Delivery (message_id) 1 : N

    Why 1-to-N: Each recipient has their own distinct delivery lifecycle, opened status, and public link token.

Delivery

Recipient State

Function & Role in Catalog

Tracks delivery progress per recipient (queued → sent → delivered → opened). It holds access_token_hash (SHA-256 of 32-byte secure random token) which powers the public recipient link (/r/:token).

  • Message (message_id) N : 1

    Why N-to-1: Multiple deliveries stem from one multi-recipient message.

  • Contact (contact_id) N : 1

    Why N-to-1: A single contact can receive multiple messages over time.

InactivitySettings

Proof-of-Life Engine

Function & Role in Catalog

Configures the proof-of-life dead man's switch: interval between check-ins, missed check-ins limit, grace period buffer, and designated trusted contact. States: active → warning → pending_trustee → released.

  • User (user_id PK=FK) 1 : 1

    Why 1-to-1: A user has only one proof-of-life configuration.

  • Contact (trustee_contact_id) N : 1 Optional

    Why N-to-1: A user selects at most one contact from their address book to verify their life status.
